# Nine Lives Audio — 优化与中文本地化说明

> 本文档记录本轮的优化项、本地化架构、以及如何自检与打包。
> 所有结论都可用 `python tools/verify.py` 复现，无需 Windows 环境。

## 1. 本地化（English / 简体中文）

### 1.1 设计

| 组件 | 作用 |
| --- | --- |
| `Models/AppSettings.Language` | 持久化偏好：`system` \| `en-US` \| `zh-CN`，默认 `system`（跟随系统） |
| `Services/ILocalizationService` | `GetString` / `Format` / `SetLanguageAsync` / `RefreshFromSettings` / `CurrentLanguage` / `IsChinese` / `LanguageChanged` |
| `Services/LocalizationService` | 代码式双语资源（245 个 key，中英一一对应），无 `.resw`/PRI，打包零风险 |
| `Helpers/AppLanguage` | 环境语言标志，供 `TimeFormatHelper`、`AudioBook` 等无 DI 的静态/模型代码使用 |
| `Helpers/Loc` | XAML 附着属性 `loc:Loc.Text/Content/Header/Placeholder`，语言切换后原地刷新 |

切换路径：设置页 → 外观 → 语言 → `SettingsViewModel.ApplyLanguageCommand` →
`SetLanguageAsync`（写设置 + 置 `AppLanguage`）→ `LanguageChanged` →
`Loc.ReapplyAll()` ＋ 各页面 `ApplyLocalization()`，**无需重启**。

### 1.2 用法

```csharp
// C#
Title = _localization.GetString("LibraryTitle");
Message = _localization.Format("DaysAgo", 3);
```

```xml
<!-- XAML：不需要代码后台 -->
<Button loc:Loc.Content="SaveSettings"/>
<ToggleSwitch loc:Loc.Header="HideFinished"/>
<TextBox loc:Loc.Placeholder="EnterUsername"/>
```

### 1.3 为什么发布目录里有很多语言文件夹

应用自身的界面语言**只有两套**（`en-US` / `zh-CN`），设置页里也只有
「Follow system / English / 简体中文」三项。发布目录（`binpublish`）里那一堆
`cs/ de/ es/ fr/ it/ ja/ ko/ pl/ pt-BR/ ru/ tr/ ...` 文件夹**不是本应用的翻译**，
而是 NuGet 依赖（Microsoft.WindowsAppSDK、CommunityToolkit、.NET 基础库等）
自带的**卫星资源程序集（satellite assemblies）**，每个语言一个子目录。

现在 `NineLivesAudio.csproj` 里加了：

```xml
<SatelliteResourceLanguages>en;zh-Hans</SatelliteResourceLanguages>
```

即只保留英文 + 简体中文，其余语言目录在 `dotnet publish` 时被裁掉（包体更小，
目录也清爽）。这不影响应用自己的中英文切换——那套资源是代码里的字典，与这些
文件夹无关。

### 1.4 规则（由自检脚本强制）

1. 新增 key 必须**同时**写入 `en-US` 与 `zh-CN` 两个字典，否则 `verify.py` 失败。
2. `Format` 模板里的 `{0}`… 数量必须与调用点实参数量一致。
3. `loc:Loc.*` 只能用在支持对应属性的控件上（`TextBlock->Text`、`Button->Content`、
   `ToggleSwitch/ComboBox/TextBox/PasswordBox->Header`、`TextBox/PasswordBox/ComboBox->Placeholder`）。
4. 使用 `loc:` 的文件必须声明 `xmlns:loc="using:NineLivesAudio.Helpers"`。

## 3. 自检（`tools/verify.py`）

```bash
python tools/verify.py
```

15 组检查，全部离线、跨平台：

1. 所有 `.xaml` / `.csproj` 是良构 XML
2. C# 花括号/圆括号/方括号配平（忽略字符串与注释）
3. 单个 XAML 内无重复 `x:Name`
4. XAML 引用的事件处理器在代码后台存在
5. 控件名/成员交叉校验
6. 本地化 key：中英集合一致，且代码/XAML 引用的 key 都存在
7. `Format` 实参数量与模板占位符一致
8. `loc:Loc.*` 与控件类型匹配
9. DI 图：所有构造函数依赖都已在 `App.xaml.cs` 注册（且不会依赖「注册为接口」的具体类）
10. 应用 XAML 引用的 `StaticResource/ThemeResource` key 都有定义
11. 打包一致性：资源文件、发布配置、TFM 三处一致（csproj/脚本/README）、`installer.iss` 版本与输出目录一致、发布配置的 RID 必须在 `RuntimeIdentifiers` 内
12. XAML 命名空间声明（`xmlns:loc` 必须存在，`using:NineLivesAudio.*` 必须指向真实命名空间）
13. 缺失 `using`：使用 `KeyboardAccelerator` / `MenuFlyout*` / `ContentDialog` / `PasswordVault` 等类型时必须引入对应命名空间（这条规则是本次手工踩到后补的）
14. 「服务器连上但书库为空」回归防护：API 层必须识别 HTTP 401（不能把失败伪装成空集合）、`SyncLibrariesAsync` 必须在空结果时保留本地缓存、书库页必须响应连接恢复事件（见 §7）
15. `DataTemplate` 内的 `x:Name` 不是页面字段：代码后台一旦直接引用就是编译错误 CS0103（这条由 CI 真实编译暴露后补上，见 §8）

当前状态：**✓ all checks passed**（83 个 C# 文件 / 13 个 XAML / 256 个本地化 key）。

## 6. 跳过开头 / 跳过结尾（全局设置）

> 上一版误做成「跳到本章开头 / 本章结尾」两个按钮，已按需求**移除**（控制行两个按钮 +
> 章节菜单里的「跳到开头 / 跳到结尾」入口 + `Ctrl+←/→` 快捷键一并删除）。
> 现在只有「设置 → 播放」里的两个全局选项。

| 设置项 | 含义 | 默认 | 范围 |
| --- | --- | --- | --- |
| 跳过开头 | 书籍开始播放时自动跳过前 N 秒（每次加载书籍生效一次） | 0（关闭） | 0–600 秒 |
| 跳过结尾 | 剩余不足 N 秒时自动跳到下一章；已是最后一章则直接标记为已听完 | 0（关闭） | 0–600 秒 |

实现要点：

- 配置存在 `AppSettings.SkipIntroSeconds` / `SkipOutroSeconds`，与其它设置一起写入 `settings.json`；
  设置页用 `NumberBox`（步进 15 秒），`NumberBox` 清空时返回 `NaN`，会统一夹到 `0..600`。
- 跳过开头：`AudioPlaybackService.PlayAsync()` → `ApplyIntroSkipAsync()`；
  **只在当前位置仍处于开头区间内**才跳，续播不会往回跳；书太短（`时长 ≤ 2×跳过值`）时自动忽略。
- 跳过结尾：500ms 的位置轮询里判断 `剩余 ≤ N`，用 `_outroSkipInProgress` 防重入；
  找到下一个「开始时间 > 当前位置」的章节就跳过去，没有则
  `FlushPlaybackProgressAsync(..., isFinished: true)` 并关闭会话。
- 两者都读的是同一个 `ISettingsService.Settings` 实例，设置页保存后**无需重启**即刻生效。

**如果觉得"没生效"，按这个顺序自查**：

| 现象 | 原因 | 现在怎么确认 |
| --- | --- | --- |
| 改完数字直接去播放，毫无反应 | 旧版本里这两个框**必须先点「保存设置」**才写盘（现已改为改动即保存，400ms 防抖） | 设置 → **Settings Doctor → "Playback saved:"** 一行直接显示真正落盘的值，例如 `skip intro 30s · skip outro 60s · progress book` |
| 跳过开头没跳 | 只有当**当前位置还在开头区间内**（`位置 < N`）才跳；续播到第 10 分钟时不会往回跳 | 日志里有 `Skip intro not needed: position 600s >= 30s` |
| 跳过结尾没跳 | 必须**正在播放**、且书长 `> 2×N`（避免短书一开就被判完成）；时长未知时已改为回退到书目时长 | 日志里有 `Skip outro: continuing with '…'` 或 `Skip outro: last chapter reached` |
| 跳过结尾直接结束了 | 最后一章没有"下一章"可跳 → 按设计标记为已听完并停止 | 同上日志 |

相关诊断：`Settings Doctor` 里新增的 "Playback saved" 行会在**每次自动保存后立即刷新**，
不用重启就能判断"到底是没保存，还是保存了但没触发"。
- 播放页仍保留「上一章 / 下一章」（`Ctrl+Shift+←/→`）与章节列表（点击即跳到该章开头）。

**保存时机（本轮修正）**：以前这两个数字框要**先点「保存设置」**才写进 `settings.json`，
改完直接去播放当然"没反应"。现在改成**改动即保存**（400ms 防抖，避免每敲一个数字就写盘），
并且打开设置页回填数值时不会触发无意义的写盘（`_isLoadingSettings` 守卫）。
界面上也写明了"修改即时生效，无需点保存"。

相关文案键：`SkipIntro`、`SkipIntroHint`、`SkipOutro`、`SkipOutroHint`（中英各一套）。

## 7. 「服务器连上了，但书是空的」（已修复）

### 7.1 现象

顶部连接状态是「已连接」，书库却一片空白，没有任何报错；重启或手动下拉有时又能恢复。

### 7.2 根因

`AudioBookshelfApiService` 里所有请求都是同一个形状：

```csharp
try { ... } catch (Exception) { return new List<...>(); }   // ← 把失败伪装成"空"
```

于是网络抖动、超时、JSON 解析失败、token 过期（401）全都被渲染成「服务器说没有书」。后续链路被这个假象带偏：

1. `SyncService.SyncLibrariesAsync` 拿到空库 → `SaveLibrariesAsync(空)` → `foreach` 一次都不执行 → 不会保存任何书 → 界面自然空的；
2. `LibraryViewModel.LoadAudioBooksAsync` 里的「离线兜底」（`ShowDownloadedOnly = true` + 提示）只在**抛异常**时触发，而空列表不抛异常 → 兜底永不执行 → 用户既看不到书，也看不到提示。

5 个具体诱因：

| # | 诱因 | 后果 |
| --- | --- | --- |
| 1 | token 过期返回 401，`EnsureAuthenticated` 只在「无 token」时抛 | 静默空库 |
| 2 | 启动时 3 秒 token 校验超时（慢网络） | 后台同步根本没启动 |
| 3 | 分页终止条件用 `total`，服务器返回 `total = 0` 时 | 只取到前 100 本 |
| 4 | 启动同步与书库页同步并发、无合并 | 重复请求、互相覆盖 |
| 5 | `SelectedLibrary == null` 时直接 `return` | 空列表且无提示 |

### 7.3 修复

- **API 层区分"成功但空"与"请求失败"**：新增 `LastRequestUnauthorized`（HTTP 401 时置位，直到下一次请求成功才清除）与 `InvalidateSession()`；`GetLibrariesAsync` / `GetLibraryItemsAsync` 对 401 单独处理，不再静默吞掉。
- **空结果不再覆盖缓存**：`SyncLibrariesAsync` 在「服务器返回 0 个库」或「某个库返回 0 本书」时打警告并保留本地数据。
- **401 有明确提示**：书库页检测到会话失效 → 清掉内存 token、状态切换为「未连接」、弹一次「登录已过期，请在设置中重新登录」。
- **离线兜底可自动恢复**：兜底只显示已下载书籍，并记录「是程序自己开的」；服务器恢复后自动关掉该筛选并提示「服务器已恢复连接，已显示全部书籍」，不会覆盖用户手动打开的同名筛选。
- **连接恢复自动刷新**：书库页订阅 `ConnectivityChangedMessage`，服务器重新可达时用 `DispatcherQueue` 回主线程重新拉取。
- **分页终止条件改为「返回不足一页即结束」**，同时保留 `total > 0` 的校验，并加 200 页上限保护。
- **同步合并**：`_librariesLock` 让并发的同步排队复用同一次结果，启动同步与页面加载不再重复下载。
- **启动不再依赖 3 秒校验**：后台同步服务总是启动（`SyncNowAsync` 自己会在未登录时跳过），校验超时从 3s 放宽到 8s。
- **空库不再静默**：`SelectedLibrary == null` 时自动选第一个库；真的没有库时刷新空状态文案。

### 7.4 自检

`tools/verify.py` 新增第 14 组检查，锁定以上不变量（已用「故意改坏」的方式验证会报错）：

```
✗ [silent-fail] AudioBookshelfApiService: ... GetLibrariesAsync() swallows HTTP 401
✗ [silent-fail] SyncService.SyncLibrariesAsync must bail out when the server returns no libraries
✗ [silent-fail] LibraryViewModel must reload when the server becomes reachable again
```

## 9. 章节跳转与时长显示（本轮修复）

### 9.1 现象

1. 播放页打开「章节」模式时，**播到下一章的那一瞬间**，右侧剩余时间/时间刻度会突然变成**整本书**的长度；
2. 有些多文件（一章一个 mp3）的书，时长显示/跳转位置看着不对。

### 9.2 原因

| # | 原因 | 说明 |
| --- | --- | --- |
| 1 | 时间文字被两套代码同时写 | `PlaybackService_PositionChanged` 是章节维度，`UpdateControlsUI()` 却无条件写 `ViewModel.CurrentPositionText/RemainingTimeText`（**全书维度**）。切章会触发 `TrackChanged`/状态变化 → `UpdateAllUI()` → 把章节刻度覆盖成全书刻度 |
| 2 | 章节不覆盖整条时间轴时章节上下文丢失 | 章间有间隙（片头片尾未被章节覆盖）时 `FindChapterForPosition` 返回 `-1` → `CurrentChapter == null` → 章节模式无处可画，回落到全书 |
| 3 | 每文件时长来自服务器元数据，可能缺失 | 累加表出现 0/重复项时：总时长变 0、`DetermineStartingTrack` 误判到最后一个文件、章节偏移全错 |

### 9.3 修复

- **单一渲染入口** `RefreshProgressDisplay(TimeSpan?)`：章节模式 → 全章节维度；否则 → 全书维度；章节未知时也回落全书，**不再留旧值**。`UpdateControlsUI()` 改为调用它（拖拽时跳过）。
- **章节间隙**：二分查找失败时回落到「开始时间 ≤ 当前位置的最后一个章节」，章节上下文不再丢。
- **时长自愈**：`ReconcileTrackDuration(trackIndex, 解码器实测时长)`——每打开一个文件，就用解码器给出的真实长度校正累加表（差值 ≥ 1s 才动），总时长与所有章节偏移同步修正。
- **元数据缺失兜底**：累加表不是严格递增时，`RebuildDurationsFromFiles()` 用 `AudioFileReader` 直接读每个文件的头信息重建。
- **跨文件跳转不再有杂音**：`SeekAsync` 先按 `autoPlay: false` 打开目标文件，落位后再播放（之前会先从 0 秒响一下）。

### 9.4 「跳转是不是按章节」的核对结论

**是**。章节的 `Start/End` 是**全书秒数**，跳转链路：

```
点击章节 / 上一章 / 下一章
  → IAudioPlaybackService.SeekToChapterAsync(i)
  → SeekAsync(TimeSpan.FromSeconds(chapters[i].Start))     // 全书时间轴
  → SeekAsync: 用累加表算出「第几个文件 + 文件内偏移」
  → 播放器落位，并直接设置 _currentChapterIndex
```

数值核对（一份 3 文件 / 6 章节、总长 2:30:00 的书）：

| 目标 | 期望 | 计算结果 |
| --- | --- | --- |
| 第 3 章（1:00:00，正好是第 2 个文件开头） | 文件 2，偏移 0:00:00 | ✅ 文件 2 / 0:00:00，回读位置 1:00:00 |
| 第 4 章（1:30:00，第 2 个文件内 30 分处） | 文件 2，偏移 0:30:00 | ✅ 文件 2 / 0:30:00，回读位置 1:30:00 |
| 第 5 章（2:00:00，单文件书） | 直接 seek 2:00:00 | ✅ |
| 元数据里每文件时长都是 0 | 修复后总时长正确 | ✅ 2:29:58（实测之和） |

> 仍未覆盖：本环境没有 .NET 运行时，上面的核对是**按同一套算法手工复算**，真正的单元测试还缺（`NineLivesAudio.Tests` 尚未建立）。

### 9.5 播放页「全书 / 章节」开关会被记住

**之前的行为**：开关状态只存在 `PlayerPage` 的字段里，而 WinUI 每次导航都会**新建页面实例**
（播放页 → 书库 → 返回），于是开关又变回「全书」——不是忘了刷新，是状态压根没保存。

**现在的行为**：

- 开关值写入 `AppSettings.PlayerChapterMode`（`settings.json`），切页、重启都保持；
- 代码内部改动（例如这本书没有章节、自动关掉章节模式）用 `_suppressChapterModeSave` 抑制保存，
  **不会覆盖用户的选择**；
- 默认值仍是「全书」，即首次使用看到的是全书时长，想看章节时长手动拨一下，之后就一直记住了。

也就是说：两种都能看，只是不再由程序擅自替你切回去。

## 12. 时间轴自愈（位置 / 章节时间单位错乱）

### 现象
- 播放一打开位置就是 **16:20:24** 这种明显不可能的值（`Skip intro not needed: position 58824s >= 35s`）；
- 章节列表里的时间/跳转位置对不上，跳过去落在错误的地方或直接停住；
- 书的总时长显示得离谱（1000 倍）。

### 根因
时间轴由三份数据拼成：`userMediaProgress.currentTime`（秒）、`chapters[].start/end`（秒）、
`audioFiles[].duration`（秒）。只要其中一份被写成**毫秒**，就会出现"差 1000 倍"的现象，
而且一旦被存进本地库，每次打开都会重新按错的数值续播 —— **会自我固化，越用越错**。

### 现在的处理（`Services/AudioPlaybackService.cs`）

| 场景 | 检测方式 | 处理 |
| --- | --- | --- |
| 续播位置 > 书长 | 书长已知且 `position > duration × 1.02` | 若 `position / 1000 ≤ duration` 判为毫秒 → 除以 1000；否则判定为脏数据 → **从头开始** |
| 章节时间 > 书长 | `max(chapter.End) > duration × 1.02` | 全部章节 `start/end ÷ 1000`，并记 `WARNING` |
| 轨道表比真实文件长 1000 倍 | 打开第一个真实文件，比较"表里这一轨的预期长度 / 解码器读到的长度"，比值落在 100–10000 之间 | 整个轨道表、章节、续播位置一起 ÷ 1000，并**回写数据库**，下次打开不再错 |

修正后会弹一条提示（中英各一套，`PositionCorrected`），并且把修正结果写回本地库，
不会每次打开都重复修正。若数值本来就正常，这三个检测都不会触发（容差 2%）。

### 一次性诊断日志
每次载入书本会打一行汇总，排查时只需看这一行：

```
[Playback] Loaded '书名': book 16:20:24, resume 00:00:58.824, start track 1/12, chapters 42 (first 0s, last 58320s)
[Playback] Chapter jump #7/42 '第七章' -> 03:15:00 (raw start 11700s, book duration 16:20:24)
```

- `resume` 与 `book` 量级不一致 → 就是位置单位问题；
- `last` 章节秒数 > `book` 秒数 → 就是章节单位问题；
- 两者都正常、跳转位置也对 → 问题在别处（此时这条日志足以定位）。

## 14. 章节开头/结尾识别与跳转（2555 章的长书）

### 从用户日志读到的真实情况
```
[Playback] Loaded '全职高手…': book 14.07:13:31 (≈343 h), resume 16:38:35,
           start track 112/2555, chapters 2555 (first 0s, last 1235434s)
```
- 书是 **2555 个文件 / 2555 章 / 343 小时**，`resume` 与 `book` 量级一致，`start track 112` 也对得上
  → **不是**之前猜的"毫秒/1000 倍"问题，时间轴本身是自洽的。
- 日志里没有一条 `Chapter jump`，说明跳转请求根本没走到播放层，用户看到的是"点了没反应"。

### 真正的原因（两处）
1. **章节时间与文件边界是两套独立估计**。章节 `start/end` 来自 `media.chapters`，
   跳转却要落到"第几个文件 + 文件内偏移"，用的是 `audioFiles[].duration` 累加出来的轨道表。
   两者按文件四舍五入，误差会**累积**：每文件差 1–2 秒，到第 300 章就偏了几分钟 ——
   跳过去"像是跳到了别的章节"。
2. **章节选择器不可用**。原来是 `MenuFlayout`（MenuFlyout）一次性创建 2555 个菜单项，
   既卡顿又**不显示任何时间**，用户无法判断"这一章从哪儿开始、多长"。

### 现在的做法
| 改动 | 位置 |
| --- | --- |
| 章节与文件 **1:1 时，章节 start/end 直接取自累计文件表**（文件才是播放器真正 seek 的目标）；每次轨道时长被校正后**重新对齐** | `AudioPlaybackService.AlignChaptersToTracks()` |
| 章节选择器改为 **虚拟化 `ListView` 的 Flyout**：显示 `序号 · 标题 · 开始时间 · 时长`，2555 章也能秒开，打开时自动滚到当前章，点击即跳 | `Views/PlayerPage.xaml(.cs)` |
| 跳转时打日志：`Chapter jump #501/2555 '标题' -> 06:12:00 (raw start ...)` | `SeekToChapterAsync` |

> 说明：章节数 ≠ 文件数时（例如一个 m4b 内含全部章节）不做对齐，完全沿用服务器给的时间。

### 验证要点
1. 播放任意一章 → 打开「章节」→ 列表应显示 `501 · 第501章标题 · 06:12:00 · 08:13`，且自动停在当前章。
2. 点其中任意一行 → 日志出现 `Chapter jump #N …`，进度条和标题立即变成该章。
3. 上一章/下一章按钮 → 落在该章**开头**（0 秒处），而不是差几十秒。

## 15. 书库加载速度

### 原来的时间都花在哪（用日志对出来的）
```
32.260 LoadAudioBooksAsync started
32.267 Loaded 309 audiobooks from database        ← 本地读库只用了 7 ms
32.267 Triggering SyncService for fresh server data...
33.879 Synced 1 libraries                          ← 网络同步 1.6 s（大头）
33.883 Reloaded 309 audiobooks from database after sync
33.886 Reloaded 309 audiobooks from database after sync   ← 又跑了一遍（重复）
```
结论：**不是数据库慢，是"等网络同步" + "整页重建两次"**。
`IsLoading` 从进页面一直保持到同步结束，而 XAML 里 `IsLoading` 为真时列表是隐藏的、只显示转圈 —— 所以用户看到的就是"卡着不动"。

### 改了三件事
| 改动 | 效果 |
| --- | --- |
| **加载请求合并**（`_booksLoadInFlight` / `_librariesLoadInFlight`）：并发调用共享同一个 Task | 页面加载、切书库、断线重连不再各跑一遍，日志里那种"同一秒内两次加载"消失 |
| **缓存先上图**：本地库读完立即 `IsLoading = false` + 过滤一次，网络同步放在后面做 | 书架在 ~10 ms 内出现，转圈只覆盖真正的本地读库（缓存为空时仍保留转圈，避免闪一下"没有书"） |
| **同步后按需重绑**：比较新旧书单 `Id` 序列（`HasSameBooks`），没变化就不重建列表 | 省掉一次 309 张卡片的重新绑定；有变化才 `ReplaceRange` + 重建分组 |

同时把每次加载的耗时打进日志，便于以后对比：

```
[Library] Local load: 309 books in 7 ms
[Library] Server sync finished in 1620 ms
[Library] Server data unchanged — keeping the current list
[Library] Load completed in 1631 ms. Total books: 309, Filtered: 309
```

> 仍未做：`SyncLibrariesAsync` 目前是全量拉取 + 逐本 upsert。书库再大（数千本）时，
> 应改成增量同步（按 `lastUpdate` 水位线只拉变化的条目）—— 这会动同步协议，需要单独一轮。

## 19. 跳过开头/结尾改为「每章生效」（本次真正的需求）

之前这两个设置只在**整本书**层面生效：`跳过开头 35 秒` 只跳过全书开头，
`跳过结尾 15 秒` 只在全书的最后一章末尾触发。所以听第 118 章时毫无作用 ——
用户说的"跳转开头和结尾多少多少秒"其实是要**每一章都套用这个秒数**。

现在（`Services/AudioPlaybackService.cs`）：

| 行为 | 触发时机 | 逻辑 |
| --- | --- | --- |
| 每章跳过开头 N 秒 | 进入任意一章（自动续播、下一章、手动跳章） | 若当前位置还在该章 `[Start, Start+N)` 内，则 seek 到 `Start + N`；**每章只跳一次**，同章内手动回退不会再被弹走 |
| 每章跳过结尾 N 秒 | 播放中每 500ms 检查 | 当 `本章 End − 当前位置 ≤ N` 时，直接进入下一章（最后一章则按既定规则标记听完并停止） |
| 防误伤 | 章节长度 ≤ 1.5×N 时不动 | 避免 30 秒的短章被整章跳掉 |
| 可观测 | 每次触发都打日志 | `Skipping chapter intro: 63000s -> 63035s (chapter #118, skip 35s)` / `Skip chapter outro (12s left of #118) — continuing with chapter #119` |

设置页文案同步改成「每章跳过开头 / 每章跳过结尾」，提示里也写明"每一章"。

> 例：设 35 / 15 后，第 118 章（63000–63540 秒）会在 63000 处直接落到 63035，
> 播到 63525 时自动切到第 119 章并同样从 119 章开头再跳 35 秒。

## 22. 修「跳到章节结尾就卡死」— 计时器里绝不再重载播放器

现象（用户截图，第 130/2555 轨，进度 09:04 / -00:14）：设了跳过结尾 15 秒后，
播到剩 14 秒时画面停住、不进入下一章、窗口「未响应」。

### 原因

上一版让位置计时器（线程池线程，每 500ms）直接调用 `SeekToChapterAsync` →
`SeekAsync` → 跨文件分支，而那里会 **`Dispose()` 一个还在播放的 MediaPlayer**，
再新建一个。跨文件中途销毁正在播放的媒体对象会把媒体线程挂住，UI 线程随后
等它 → 整个窗口未响应。日志上只会看到最后一次 `Skip outro`，之后没有任何输出。

### 现在

| 规则 | 说明 |
| --- | --- |
| 计时器只做**同文件**定位 | 新增 `SeekWithinCurrentTrack()`，只改 `PlaybackSession.Position`，绝不加载/销毁播放器 |
| 跳过结尾 = 跳到文件末尾 | 档案结尾即章节结尾 → 跳到 `轨道长度 - 0.35s`，交给**一直正常的** `MediaEnded` 自动续播；章节结尾在文件中间 → 跳到该处，下一章的跳过开头接着生效 |
| 跳过开头同样限定同文件 | 目标不在当前文件里就延后（下一 tick 或自动切章后处理），不再引发跨文件加载 |
| 章节状态每章只处理一次 | `_skipChapterIndex` + `_introSkipDone` / `_outroSkipDone`，避免反复 seek |
| 跳过判定搬到 UI 线程 | 计时器只投递一次（`TryEnqueue`），消息、滑块更新都在 UI 线程完成 |
| 载入新流前先 `Pause()` | `LoadStreamAsync` 里销毁前先暂停，其他跨文件路径（手动跳章）同样受保护 |
| 停滞看门狗 | 状态是 Playing 但位置 8 秒不动 → 打 `Position has not moved for Ns …` WARNING，下次一看日志就知道卡在哪 |

新版日志（章节结尾）：

```

[Playback] Stream auto-advancing to track 131/2555
[Playback] Skip intro: 68562s -> 68597s (chapter #131, skip 35s)

## 24. 回传时长被放大成几百小时（`timeListened` 用错了语义）

用户用第三方统计看到的：`分日听书统计 356.35 小时 / 580.33 小时`，而"有效计入听书"只有
`3.70 / 4.48` 小时 —— 服务器端的原始时长被放大了两个数量级。

### 原因

Audiobookshelf 的 `POST /api/session/:id/sync` 里 `timeListened` 的定义是
**"距上次同步期间听了多少秒"（增量）**，服务端会把它累加到 `session.timeListening`。
我们之前每 12 秒发的是**本次会话累计时长**，于是服务端每次同步都把整段会话再加一遍：
3 小时的真实收听 ≈ 900 次同步 → 累计被加到几百小时。第二个问题是暂停时也在累加，
挂机时间同样被算成"听了"。

### 现在

| 项 | 行为 |
| --- | --- |
| 计时 | `TrackListeningTime()` 只在状态为 `Playing` 时按真实墙钟累加（含倍速），暂停/缓冲不计 |
| 上报 | 每次同步发**增量**（上限 120 秒），`Session sync: 67500.0s, +12s (session total 4021s)` |
| 失败重试 | 服务端拒绝时不扣减，留到下一次；上限保证不会无限膨胀 |
| 关会话 | 关闭前先补发最后一个不完整区间（<12 秒），不丢时长 |

> 注意：已经被放大的历史统计数据在服务器数据库里（`sessions` 表），要清零只能在服务器侧删除
> 相应 session 记录或用 ABS 的统计重置；本客户端修复后**只保证以后不再放大**。

  `[Cache] Purged 3 stream file(s), 1.2 GB freed (cap 2 GB)`；干净时只写 Debug。

### 27.2 日志保留（其实早就有，现在能自证）

14 天保留是之前就有的，我上一版清单说"永不清理"是看漏了。这次补的是：
- 删除时写一行 `[Logging] pruned 2 old log file(s), 8 MB freed (retention 14 days)`；
- 单文件硬上限 **25 MB**（诊断模式全开也不会一天写满磁盘），到顶时写
  `[Logging] today's log reached 25 MB — further lines are skipped`。

### 27.3 主题切换后颜色不跟随（22 处代码赋色）

`{ThemeResource}` 只对 XAML 生效；代码里 `ThemeService.Brush(...)` 拿到的是一份快照。
切到浅色主题后，书库状态点、视图模式按钮、播放页来源徽章、迷你播放器图钉、主窗口连接状态点

### 27.4 数据库断线自愈

`LocalDatabase` 全进程只持有一个 `SqliteConnection`。睡眠唤醒、外接盘/网络盘、杀毒软件锁定之后，
底层句柄可能已失效，而 `State` 仍然是 `Open`，之后每个查询都抛异常直到重启。

现在所有命令都走 `GetConnection()`：先 `SELECT 1` 探活（本地 SQLite 亚毫秒级），失败则重建连接、
重放 WAL/busy_timeout/synchronous 三条 pragma，并写
`[Database] Connection lost (SqliteException: …) — reconnected to …`。
内存库（测试）不会触发重连，避免静默丢数据。

### 27.5 中文界面残留英文

设置页还有 14 条英文说明/标签（"Settings file:"、"This will remove cached library data…" 等）
在中文界面下露出来。已全部接入本地化（`SelfSignedHint`、`SyncNowHint`、`DiagnosticsHint`…），
语言切换即时生效。

### 27.6 「进度显示：跟随章节」终于在设置里能改

`PlayerChapterMode` 一直有存有读，但设置页没有入口，只有播放页某个开关能切。现在

## 29. 1.0.7 后续修复（主页进度实时化 +题底色）

这一节是 1.0.7 打包之后、根据实际使用反馈补的两处，不改变版本号语义，随下一次构建一起发。

### 29.1 主页「九命」的进度/时长不跟着服务器走

现象：主页那九行的圆环和时间长时间不动，**只有点播放**时才显示最新位置。

原因有两处，都不是"刷新不够快"，而是同步逻辑里**用本机时钟去和服务器时间戳比较**：

| 位置 | 旧逻辑 `→` 后果 |
| --- | --- |
| 增量水位 `_lastProgressPullTimestamp` | 写的是 `DateTime.UtcNow`（本机），却拿去和服务器返回的 `lastUpdate` 比 `→` 只要本机时钟快几秒，服务器上的更新永远"不比水位新"，整批被跳过 |
| 位置采纳 `progress.LastUpdate > localTimestamp` | `localTimestamp` 是本地写库时打的 `DateTime.UtcNow` `→` 同样的偏差让服务器位置永远"更旧"，一秒钟也写不进来 |

播放走的是单书进度接口（`ResolveInitialProgressAsync`），不经过这两个判断，所以只有那一刻是对的。

现在：

- 水位改为**本批服务器时间戳的最大值**（同源时钟比较，本机时钟快慢无关）；
- 位置**以服务器为准**，唯一例外是该书还有"离线待上报"的本地进度（`PendingProgressUpdates` 里有它），避免把飞机上听的进度覆盖回去；
- 一次拉取只要真的改了什么，就发 `SyncCompletedMessage`，主页/书库立刻重载，不必等下一个 tick；
- **打开主页就拉一次**（先显示本地快照，服务器数据回来立即替换），重复拉取由独立信号量挡住。

自证日志：

```
[Sync] POSITION CHANGE '某本书': 00:12:03 → 00:31:47 (server 2026-11-14T18:22:10Z, local 2026-11-13T09:11:02Z)
[Sync] Progress synced for 3 of 5 server entries (2 unchanged, 0 awaiting library import), watermark 2026-11-14 18:22:10Z
```

补充：正在播放的那一本仍由播放器实时驱动（`PositionChangedMessage`，1 秒一次），同步会主动跳过它，两边不打架。

### 29.2 设置页等页面在深色主题下露出浅色底

现象：主题选了「深色」，卡片是深色的，但页面**背景**是浅灰白，标题几乎看不清。

原因：只有 `HomePage` 给 `Page` 设了 `Background`，其余页面（设置、书库、播放器、详情、下载、统计）都是透明，透出窗口底层的
`ApplicationPageBackgroundThemeBrush`（在 Mica/系统浅色下就是浅色），于是"深卡片 + 浅底"混搭。

现在：六个页面统一 `Background="{ThemeResource VoidDeepBrush}"`（深色 `#050810` / 浅色 `#F6F7F9`），
`MainWindow` 的启动遮罩与错误面板也改用调色板键，不再依赖系统色。

## 33. 1.0.11：暂停即刷新进度

### 33.1 只有重启才刷新进度 —— 根因

`SyncService._activeItemId` 在**开始播放**时被设为这本书，但**从来没有被清掉**（暂停、停止都不清）。
于是每 5 分钟的进度拉取都以"这本书正在播放，会话拥有进度"为由跳过它，主页/详情页读的又是本地库 ——
只有重启（字段回到 `null`）那一次才会读到服务器值。

现在：

- `PauseAsync()` 立刻 `SetActivePlaybackItem(null)`，恢复播放时重新设回；
- 暂停、停止、每 12 秒的会话同步，写库成功后都会发 `PlaybackProgressSavedMessage`；
- 主页按这本书就地更新圆环/时长/顶部总计；书详情页重算 `N% complete (x / y)` 与进度条。

书详情页的 `Status`（详情卡片里那行）是加载时一次性生成的静态行，**不会**跟着变 —— 顶部那行进度文字和进度条会。

### 33.2 其它两处

- 导航栏左上角那个没用的返回箭头（`IsBackButtonVisible="Auto"` 在单页导航下总会画出来）已移除；
- 主页不再把第一行标成"选中"（深色块 + 金色竖条），只保留鼠标悬停反馈。

## 34. 1.0.12：刷新不重排书库、主页与书库同一份进度、返回时侧栏跟着走

### 34.1 书库刷新会重新渲染整页

`LoadAudioBooksCoreAsync` 每次都用 `ReplaceRange` 换掉整个集合，`ItemsRepeater` 收到 Reset 就重建所有卡片 ——
表现是刷新时书库闪一下、滚动位置丢失。

现在集合顺序与书目都没变时走 `MergeBooks`：把新的进度值**复制到已有对象**上，
`AudioBook` 的 `CurrentTime/Progress/IsFinished/IsDownloaded` 会发 `PropertyChanged`，卡片就地更新。

### 34.2 书库能看到新进度，主页看不到

根因在写库那一侧：`SavePlaybackProgressAsync` 只写 `PlaybackProgress` 表，**从不更新 `AudioBooks` 行**，
而主页（`GetRecentlyPlayedAsync`）与书库（`GetAudioBooksByLibraryAsync`）读的都是 `AudioBooks`。
于是"书库刷新"看起来更新了（那条路径来自服务器进度回写），主页的时长却还是老值。

现在写进度的同时把 `CurrentTimeSeconds / Progress / IsFinished` 镜像到 `AudioBooks`，两处读同一份数据；
另外书库也订阅 `PlaybackProgressSavedMessage`，暂停即更新卡片，不必等刷新。

### 34.3 从播放器返回后侧栏还停在"播放器"

`PlayerPage` 的返回箭头直接 `Frame.GoBack()`，绕过了侧栏，所以内容变成书库、高亮却还在播放器上。
`NavigationService` 现在监听 `Frame.Navigated`，按目标页把 `SelectedItem` 同步到对应的菜单项
（设置页对应底部齿轮；详情页这类不在侧栏的页面保持不动）。

## 35. 1.0.13：主页每次显示都重新读一遍（日志定位）

用户提供的日志里，同步链路本身是好的：

```
[Sync] POSITION CHANGE '全职高手…': 2.02:07:33 → 2.02:07:33 (server 09:18:11, local 09:16:51)
[Sync] Progress synced for 1 of 12 server entries (11 unchanged…), watermark 2026-11-17 09:18:11Z
```

位置与服务器一致、水位在推进、`synced=1` 会广播重载。问题在**主页没有再加载**：整份日志里
`[Home] Loading Nine Lives...` 只出现在 17:14:03 启动那一次，之后无论怎么切页面都没有第二次。

两个原因叠在一起：

1. `HomePage.OnUnloaded` 里写了 `this.Loaded -= OnLoaded;` —— `Frame` 会缓存页面实例，
   第二次进入主页时 `Loaded` 仍会在同一个对象上触发，但处理器已经被摘掉了；
2. 同一个方法里 `Dispose()` 了视图模型，而它的 `Dispose` 就是 `UnregisterAll`，
   于是"同步完成/位置已保存"这两种广播也收不到了。

现在主页改用 `OnNavigatedTo`（每次导航都会调用，包括复用缓存实例）做刷新，不再依赖 `Loaded`；
视图模型不随页面卸载而 Dispose（`WeakReferenceMessenger` 用的是弱引用，页面真被回收时不会泄漏）。
书库、下载、播放器三个页面有同样的写法，一并改掉；下载页在 `Loaded` 里重新挂回集合变更事件。

顺带：主页每次进入会拉一次服务器进度，加了 5 秒节流，来回切页面不会打接口。

## 36. 1.0.14：书库改成后台静默刷新

1.0.12 之后列表不再重建，但定时同步仍然走"可见刷新"的路径：每次同步完成都调 `LoadLibrariesAsync`
（`Clear` + 重新填充图书馆列表）和 `LoadAudioBooksAsync`（置 `IsLoading`、还会再向服务器要一次书库），
所以书库页看起来一直在"加载"。

现在分开了两条路：

| 触发 | 行为 |
| --- | --- |
| 定时同步完成（默认每 1 分钟） | **只读数据库**并 `MergeBooks` 到现有对象；不置 `IsLoading`、不重建、不访问服务器。日志：`[Library] Background refresh merged N books (idle, no re-render)` |
| 进入书库页 | 30 秒内刚拉过就什么都不做（页面实例被缓存，`Loaded` 会反复触发）；超过 30 秒才重新走完整加载 |
| 点刷新按钮 | 照旧：显式拉书库 + 进度，显示刷新状态 |

另外把同步节奏也拆开了：**进度每分钟拉一次，书库元数据每 10 分钟拉一次**（`SyncNowAsync` 内部判断，
"点刷新"和每次启动仍会完整拉一遍）。之前两者同频，等于每分钟下载一次全部书库条目。

## 37. 1.0.15：深色模式下原生标题栏也是深色

标题栏不是 XAML 画的，是 DWM 画的。之前只设置了 `AppWindow.TitleBar.*` 的颜色，
这套 API 只在"系统支持自定义标题栏"时生效；否则（Windows 10、或系统把标题栏按系统主题绘制）
赋值会被静默忽略 —— 于是窗口内容是深色，标题栏仍然是白的。

现在给两个窗口都传入 `HWND`，并且用 DWM 属性同时设置：

| 属性 | 作用 |
| --- | --- |

| `DWMWA_CAPTION_COLOR`（35，Win11 22H2+） | 直接把标题栏刷成 `#050810`（浅色 `#F6F7F9`） |
| `DWMWA_TEXT_COLOR`（36） | 标题文字/按钮颜色，深色用 `#E0E0E8` |

调用失败（老系统不支持某个属性）不会报错，退回 `AppWindow.TitleBar` 那套颜色。
切换主题时 `ThemeService.Apply` 会把这两个窗口的标题栏一起重刷。迷你播放器窗口同样处理。

## 38. 1.0.16：播放缓存（会话级，两轨）+ 封面存进软件包

### 38.1 流式播放原来是每次都重新拉

`PlaybackSourceResolver` 先看有没有整本下载，没有就用 `STREAM`：每"轨"（一章一个音频文件）一个
HTTP 地址，边下边播。切走的那一轨，缓冲区就丢了 —— 回退、重听、甚至切回来都要重新从服务器拉。

### 38.2 现在：边听边缓存，只存两轨，退出即清

新增 `StreamCacheService`，缓存目录 `<数据目录>\streamcache\<书 ID>\`：

| 行为 | 细节 |
| --- | --- |
| 什么时候缓存 | **点播放时**才开始，不在浏览时预下 |
| 存多少 | **每本书两轨**（正在听的 + 下一轨），换书时删掉其它书的目录 |
| 播放优先级 | 该轨已在磁盘 → 直接读本地文件；否则照常流式播放，同时后台下载，**下次**这条轨就从磁盘读 |
| 预取 | 当前轨成功打开后，后台把下一轨也存下来，切轨不再等网络 |
| 清理 | 启动时**清空整个缓存**，退出（窗口关闭）时再清一次；所以不会跨会话堆积 |
| 完整性 | 写入 `.part` 临时文件，完成才改名；损坏/截断的文件在播放失败时自动删除并重新下载 |

**进度完全不受影响**：进度 = 轨道起始偏移 + 播放器在轨内的位置，写进 `PlaybackProgress` 并镜像到
`AudioBooks`；缓存只决定这段音频从磁盘还是网络读。所以"缓存了 2 章"不会让进度变成 2 章。

按你的书算：8 分钟/轨、128 kbps ≈ 8 MB/轨，两轨约 **16 MB**，退出就没了。

### 38.3 封面现在真的在软件包里

以前 `CoverPath` 存的是服务器地址（还带 token），所以每张封面都是实时请求，离线就空白。
现在第一次显示封面时会下载到 `<数据目录>\covers\`（文件名取自 item id），之后的显示全部读本地文件：

- 便携版整包拷走，封面跟着走；
- 断网也能看到封面；
- 重新登录换了 token 也不会重新下载（文件名按 item id 生成，不吃 URL 里的 token）；
- 受「自动下载封面」开关控制（默认开）。

内存里仍有 300 张的解码缓存，那层不变。

## 39. 1.0.17：从日志里查出的四个问题

用户提供的日志（`Build: 1.0.16.0 (build 1708d56)`，293 行）跑得很干净 —— 没有一条 WARN/ERROR ——

### 39.1 播放缓存其实一次都没生效

原因：`StreamCacheService.ClearAsync()` 里调用了 `_shutdown.Cancel()`，而 `MainWindow` 在**启动时**就调用

立刻抛 `OperationCanceledException`，被当成"缓存失败"默默吞掉。

现在 `ClearAsync()` 只删文件，取消令牌只在 `Dispose()` 时触发；下载成功后改用 INFO 打印一行，
方便在日志里确认缓存真的在工作：

```
[StreamCache] Stored track 360 of '34a85e6c…' (7712 KB) — next play of this track is local
```

### 39.2 一次同步触发了五遍刷新

22:21:12 那一秒里出现 5 条 `[Library] Background refresh merged 309 books`、3 条 `LoadLibrariesAsync started`、
3 条 `Triggering SyncService`。

原因：`HomeViewModel` / `LibraryViewModel` / `PlayerViewModel` / `DownloadsViewModel` 都是 `AddTransient`，
而这些 ViewModel 的构造函数会向 `WeakReferenceMessenger` 注册订阅。页面被 `Frame` 缓存复用、
再次显示时不会重新构造 —— 但**每次新建页面实例就会多一个 ViewModel**，旧的那个永远不会注销，
于是每进一次书库就多一个"收到同步完成就刷新"的听众，日志里就是 5 份同样的工作。

现在这四个改为 `AddSingleton`（它们本来就是应用级状态：筛选、滚动、当前曲目），
订阅只有一份；`BookDetailViewModel` / `SettingsViewModel` / `StatsViewModel` 保持 Transient（按书/按次）。

### 39.3 同步完成消息发了两遍

`SyncProgressAsync` 在有变化时发一条，`SyncNowAsync` 结束时又发一条，同一次同步触发两轮重载。
现在全量同步期间用标志位抑制进度同步那条，一次同步 = 一条消息。

### 39.4 日志太吵

- `POSITION CHANGE` 以前对每本书都打 INFO，启动时 12 行、其中大多是 `2.05:48:24.6587478 → …795`（差 1e-7 秒）。
  现在只有位置真的移动超过 1 秒才打 INFO，否则 DEBUG。
- 书库页加载过程的 `LoadLibrariesAsync started` / `Loaded 1 libraries` / `Triggering SyncService` 等降为 DEBUG，

顺带修了并发问题：`LoadAudioBooksCoreAsync` 里"30 秒内不重复向服务器要书库"的判断是读后写，
三个并发调用会同时通过；现在用 `Interlocked` 门闩保证只有一个能进去。

## 42. 1.0.20：书库分页并行拉取、日志按体积滚动

### 42.1 书库元数据：从串行分页改为并行

- `total` 缺失（老版本服务端返回 0）→ 退回原来的串行循环；
- 最后一页恰好是满页（说明服务端实际比 `total` 多）→ 从下一页继续串行补齐，不会漏书。

## 43. 1.0.21：点播放到出声的 1.4 秒花在哪

用 `app_2026-11-5.log` 的时间线（1.0.21 之前的构建）：

```
11:54:26.909  [Playback] Session started
11:54:26.918  [Playback] Stream URL obtained, 2555 tracks      ← 9 ms
11:54:28.347  [Playback] Stream loaded                          ← +1429 ms
11:54:28.806  [StreamCache] Stored track 372 ...                ← 播放开始之后
```

结论：**延迟不来自缓存下载**。拿流地址只花 9 ms，1443 ms 全在"打开网络音频流"——MediaPlayer 要连服务器、
请求第一块数据、初始化解复用器和解码器。缓存下载发生在播放开始**之后**、在后台并行，不占播放启动路径。

这一轨当时也没命中缓存（日志里没有 `served from cache`），首次播放某本书必然走网络；命中缓存时是 0.28 s。

本轮改动：

1. **复用 MediaPlayer 实例**。以前每次切轨都 `new MediaPlayer()` 再 `Dispose()`，等于每次重建整套媒体管道。
   现在复用同一个实例，只换 `Source`；打开失败时才丢弃重建。
2. **轨内偏移小于 2 秒不再 seek**。对网络流，一次 seek 就是一次新的 range 请求。
3. **把 1.4 秒拆成可核对的日志**：
   - `[Playback] Stream URL obtained, N tracks (first: /api/items/…/file/371 (query: token))`
     —— 能看出是普通文件还是 HLS/转码会话（`?transcode=`、`.m3u8`）；
   - `[Playback] Media opened in 1429 ms (stream, player reused)`；
   - `[Playback] Seeked into track: 00:03:12`。
4. **播放中不再拉全量书库**。日志里 11:56:12 那次 `Load completed in 12407 ms` 正好发生在播放期间
   （用户切到了书库页）。现在播放/加载状态下，书库元数据刷新从 30 秒节流改为 10 分钟，避免和音频抢带宽。

下一步要看 `Media opened` 与 `Stream source` 两行：如果是 HLS/转码，可以改成直接请求
`/api/items/{id}/file/{ino}` 跳过服务端转码，那一千多毫秒会大幅缩短。

## 44. 1.0.22：点播放的两个 5 秒空档

`app_2026-11-6.log`（1.0.21）把延迟拆开之后，看到的是两段：

12:09:09.499  [Playback] Session started            ← 5779 ms 空档，没有任何日志
12:09:09.509  [Playback] Stream URL obtained ...
12:09:16.375  [Playback] Media opened in 6837 ms
```

1. **5.8 秒**：`POST /api/items/{id}/play`（拿播放会话和音轨地址）。你的服务器上这个请求就是这么慢。
2. **6.8 秒**：打开音频流。同一台服务器，上一次只要 1.4 秒 —— 因为这一次**同时**在跑：
   - 会话首次的全量书库同步（309 本 × 4 个并行请求，`12:09:16.731 [Sync] Synced 1 libraries`）；
   - 当前轨的缓存下载（`PrepareTrackAsync` 在缓存未命中时立刻开始下载同一轨）。

   三条大流量挤在一起，播放打开就被拖慢了。

本轮改动（都对得上日志里的证据）：

1. **播放会话缓存 + 预取**。会话里带的是音轨地址，同一本书 10 分钟内复用；打开书籍详情页时在后台先请求一次
   （只取元数据，不下载音频），点播放时通常已经就绪。
2. **书库全量同步避开播放**。播放/加载状态下：会话首次的全量拉取最多延后 10 分钟，之后间隔从 10 分钟拉长到 30 分钟。
3. **缓存下载挪到打开之后**。`PrepareTrackAsync` 不再在流打开期间下载同一轨；改为 `MediaOpened` 之后一起预取
   「当前轨 + 下一轨」，让首块数据独占带宽。
4. 顺手修掉日志里 `[Sync] Started with 1min interval` 连打三次的问题（`StartAsync` 并发进入）。

## 48. 1.0.26：那个「加载失败」是跨线程改集合，不是服务器出错

`app_2026-11-7.log` 里三条 ERROR 的栈都指向 WinUI 的绑定层，没有一条是网络或数据库：

```
14:07:05  LoadLibrariesAsync failed:
          ABI.Microsoft.UI.Xaml.Interop.WinRTNotifyCollectionChangedEventArgsRuntimeClassFactory
          at LibraryViewModel.LoadLibrariesCoreAsync() line 424      ← Libraries.Clear()/Add()
14:07:17  LoadAudioBooksAsync failed for library 全部书籍:
          at ABI.Microsoft.UI.Xaml.IApplicationMethods.get_Resources
          at LibraryPage_obj1_Bindings.LookupConverter()            ← IsLoading 属性触发 x:Bind
14:07:17  [Library] Delayed reconnect refresh failed:
          at XamlBindingSetters.Set_TextBlock_Text()                 ← ErrorMessage 触发 x:Bind
```

三条都出在同一处：`ReloadAfterReconnectAsync` 把「45 秒后的全量刷新」写在 `Task.Run` 里。
等待本身在后台线程没问题，但随后它直接调用了 `LoadLibrariesAsync()` / `LoadAudioBooksAsync()`，
这两个方法会改 `ObservableCollection` 和绑定属性 —— WinRT 于是尝试把一个集合变更通知从后台线程
marshal 到 UI 线程，抛异常；异常又被 catch 成 `ErrorMessage`，界面上就出现了「加载失败」。

数据没丢：同一时刻日志里有 `[Library] Local load: 309 books in 4 ms`，随后 14:07:26 再进书库也正常。

修法：

1. 那个延迟刷新改为 `RunOnUiThreadAsync(...)`，只在 UI 线程碰集合与属性；
2. `LoadLibrariesAsync` / `LoadAudioBooksAsync` 入口再做一次线程检查 —— 任何调用方从后台线程来都会先被

## 50. 1.0.28：书库那 12 秒是服务器，客户端能砍掉的都砍了

`app_2026-11-9.log` 里 1.0.27 的诊断行给出了答案：

```
15:04:50  [Sync] Library '全部书籍': 309 items in  2117 ms (4 page(s) parallel in 2114 ms)
15:04:53  [Sync] Library '全部书籍': 309 items in  1325 ms (4 page(s) parallel in 1322 ms)
15:36:04  [Sync] Library '全部书籍': 309 items in 12832 ms (4 page(s) parallel in 12832 ms)
16:22:23  [Sync] Library '全部书籍': 310 items in 14523 ms (4 page(s) parallel in 14523 ms)
16:22:36  [Sync] Library '全部书籍': 310 items in  1253 ms (4 page(s) parallel in 1253 ms)
```

同一个库、同样的四页并行，**有时 1.2 秒、有时 14.5 秒**（13 秒后又变成 1.2 秒）。进度同步也一样：
`[Home] Page shown — progress synced in 5235 ms` / `5403 ms`，而正常是 300 ms。

结论：**并行一直是生效的**，慢的是服务器本身（`cfabs.ccoff.com` 间歇性响应慢），不是客户端的翻页逻辑。
客户端只能减少请求次数，所以这一版做两件事：

### 50.1 一次请求装下整个书库

分页大小从 100 提到 500，310 本书命中「一页装完」的快捷路径 —— 从 4 次往返变成 1 次。
关键的安全改动：页大小改用**服务器实际返回的条数**（`first.Results.Count`）而不是我们请求的 `limit`。
否则服务器一旦把 500 截成 100，旧代码会把「短页」误判成「书库到底了」，直接漏掉 200 多本书。
新日志里会出现：

```
[Sync] Library '全部书籍': 310 items in 1204 ms (1 page in 1201 ms (whole library))
```

如果服务器不认 500，就还是 `4 page(s) parallel`，行为和以前一样。

### 50.2 三处调用方不再各拉一遍

主页进入、书库页进入、每分钟的定时器都会请求书库元数据。以前只有定时器那一处有节流，
于是同一分钟内可能拉两三次。现在 `SyncLibrariesAsync` 内部有 2 分钟去重，只有显式动作
（书库页刷新按钮、设置页「立即同步」、重连后的补拉）用 `force: true` 绕过。

### 50.3 已知但不在客户端解决

- 服务器 12–14 秒那几次，是它自己慢（同一份数据 13 秒后 1.2 秒就返回了）；
- 若要根治，只能服务器侧优化（SSD、减少库条目序列化体积），或客户端改用 `minified=1` 少取字段 ——
  但 minified 会丢掉 `audioFiles`/`chapters`，章节跳转和详情页会受影响，**在没有真机验证前我不动它**。

## 51. 1.0.29：从播放页返回时，书籍详情的进度不更新

现象：主页点一本有进度的书 → 详情页 → 播放 → 进播放页 → 暂停 → 返回详情页，
「N% complete (x / y)」和进度条还是**进入播放前**的位置。

原因：

1. 详情页在离开时（`Page_Unloaded`）会 `WeakReferenceMessenger.Default.UnregisterAll(this)`；
2. 暂停发生在播放页显示期间，`PlaybackProgressSavedMessage` 发出来时详情页已经不在订阅名单里；
3. 回到详情页时只重新注册了订阅，**没有主动读一次当前进度** —— 于是显示的是离开时的旧值。

修法（没有删掉播放页的返回按钮 —— 返回是主要导航方式，去掉才是问题）：

- **返回详情页时主动刷新**：正在播放这本书就用播放器的实时位置，否则读数据库里暂停刚写入的位置，
  然后重算百分比、进度条、「继续/播放」文案和章节信息；
- **详情页在前台时跟随播放**：订阅 `PositionChangedMessage`，1.5 秒节流更新同一批元素，
  所以边听边看详情页，数字也是走的。

## 55. 1.0.33：拖动进度条不再把播放器打爆

### 日志里发生了什么（`app_2026-11-12`）

一次 session 内的计数：

| 日志行 | 次数 |
|---|---|
| `[Playback] Media opened in …` | **253** |
| `[Playback] Stream ended (all tracks)` | **141** |
| `[Playback] Stream auto-advancing` | 0 |
| `[StreamCache] Stored track …` | 65 行 / **53 个不同轨道** |
| `[Playback] Session started` | 1 |

253 次「媒体已打开」全部挤在同一分钟（17:29），且 `elapsed` 依次递减
（6665 → 6430 → 5936 → … → 1713 ms），也就是 250 多个 `LoadStreamAsync` 在约 6 秒内
被连续启动、同时挂起等同一个 `MediaOpened`，随后一起醒来。

时间线对得上：17:29:33 打开播放器页 → 7 秒空白 → 17:29:40 落到 197600s 并触发跳过片头。
**这是拖动进度条**：这本书 2555 轨，从 2 小时 06 分拖到 3 小时 18 分要跨过几十上百个轨道文件，
而 `ProgressSlider_ValueChanged` 每来一次就立刻 `SeekAsync`，跨轨就立刻 `LoadStreamAsync`。

后果：
- 250 多个流同时打开 → 界面卡住、`Position has not moved for 8s`
- 缓存被写进 53 个轨道（你要的是「一本书两集」，`FilesPerBook = 2` 的修剪在并发下形同虚设）
- 141 次 `Stream ended (all tracks)`：`MediaEnded` 每加载一次就 `+=` 一次，从不 `-=`，

### 改了什么

1. **拖动时不再每格都 seek**：`ValueChanged` 只记录目标值，静置 350 ms 才提交；松手
   （`PointerReleased`）立即提交，不用等。
2. **程序自己刷新进度条不再被当成拖动**：`RefreshProgressDisplay` 写 `Value` 时用
   `_isUpdatingProgressSlider` 包住。原来靠 `FocusState` 判断，滑块被碰过一次之后就一直
   「有焦点」，于是每秒数次的自动刷新也会触发 seek。
3. **`WireMediaPlayerEvents` 改成幂等**：进入时先 `UnwireMediaPlayerEvents()`，
   同一个播放器上再怎么重复加载也只有一份处理器。

自证日志：
```

[Playback] Media opened in …        ← 一次拖动只剩一行
```

### 没测到的部分

`app_2026-11-12` 里没有 `[BookDetail] Jumped to chapter` 行 —— 你这次是在**播放器页的
章节对话框**里跳的（`[Player] Chapter dialog row activated`），1.0.32 加的详情页章节点击

## §56 1.0.34 — 详情页简介的 HTML 标签剥离

### 现象（用户截图 + `app_2026-11-15.log`）

详情页「简介」区直接显示了原始 HTML：

```
<p><b><a>&gt;&gt;全职高手冠军夜小剧场3集最新掉落！点击收听&lt;&lt;</a></b></p><p>喜马拉雅携手8082Audio…
```

### 原因

Audiobookshelf 的 `description` 字段本身就是一段 HTML（`<p>`、`<b>`、`<a>`、`&gt;`/`&lt;`/`&nbsp;`
实体），而 `BookDetailPage.xaml.cs` 把它原样塞进了 `TextBlock.Text`。`TextBlock` 不解析 HTML，
所以标签和实体原样上屏。

附的日志对这个问题没有信息量：简介内容从不打日志，日志里只有版本（1.0.32 → 1.0.33 两个
session）和播放警告。证据是截图，不是日志。

### 改了什么

1. 新增 `Helpers/HtmlTextHelper.StripHtml(string?)`：
   - `<br>`、`</p>`、`<p>`、`<li>`、标题等块级标签 → 换行；
   - 其余标签全部去掉；
   - **先去标签、后解实体**（`WebUtility.HtmlDecode`），这样 `&lt;p&gt;` 这种转义过的标签
     会保留为字面文本，不会被误当成真标签删掉；
   - `&nbsp;`（U+00A0）转成普通空格，保证 `TextBlock` 正常换行；
   - 连续空行压到最多一个空行。
2. `BookDetailPage.xaml.cs` 显示前调用它。数据库里已存的 314 本原始 HTML 不用迁移，
   显示时剥离即可覆盖全部存量数据。

自证日志（只有简介含 HTML 时才打）：

```
[BookDetail] Description HTML stripped (4821 -> 4310 chars)
```

### 没测到的部分

沙箱无 Windows，未真机验证。剥离逻辑已用截图中的真实 HTML 片段离线验证：
标签清零、`&gt;&gt;`/`&lt;&lt;` 正确解码为 `>>`/`<<`、段落换行保留、纯标签简介显示为空。
